# Core

`framework-core` is the shared package behind the widget and the login app: stores, journey logic, callbacks, stages, UI components, OAuth/OIDC, and i18n locales. It is a private pnpm workspace package (`core/package.json`) and is never published to npm. `packages/login-widget` and `apps/login-app` consume its built output, and it is the intended shared base for the Custom Components editor.

## Why a Workspace?

Core is built once and consumed as compiled modules. Consumers no longer re-compile core sources as part of their own build. This gives one compilation of the shared surface, a single place to define Svelte compile options, and a stable package boundary for other consumers.

## Build

The package builds twice from the same set of runtime modules (see `collect-entries.ts`), one output file per module:

| Output         | Config                  | Compilation              | Used for                                                            |
| -------------- | ----------------------- | ------------------------ | ------------------------------------------------------------------- |
| `dist/`        | `vite.config.ts`        | Svelte client            | Browser bundles and client hydration                                |
| `dist-server/` | `vite.config.server.ts` | Svelte SSR (`ssr: true`) | SvelteKit server rendering, which must not execute client templates |

Both trees mirror the source tree, with these emitted-name differences:

- `foo.svelte` is emitted as `foo.component.js`. `vite-plugin-svelte` re-compiles any `*.svelte.js` file in a consumer's dev server as Svelte runes source and fails with "The $ name is reserved", so the compiled output must not use that suffix.
- `foo.ts` is emitted as `foo.js`.
- `index.json` locale catalogs are emitted as `index.json.js`.

Runtime dependencies (`svelte`, `@forgerock/*`, `zod`, `qrcode`, `xss`) are external to the package and resolve from the consumer's install. Declare any new dependency that core imports in `core/package.json`.

Component styles are compiled into the JavaScript (`css: 'injected'`), and neither build emits a stylesheet. Tailwind utility classes used in core sources are generated by the consumer's own Tailwind scan, which includes `core/` (see `packages/login-widget/tailwind.config.cjs`).

Excluded from both builds and never shipped: tests (`*.test.ts`), Storybook files, mocks (`*.mock.ts`; runtime helpers consumers need live in `*.utilities.ts` instead), SvelteKit-only code (`server/`, `constants.ts`), the registry seeding templates, and build tooling.

## Commands

Run from the repository root unless noted.

| Command                                          | Description                                                                     |
| ------------------------------------------------ | ------------------------------------------------------------------------------- |
| `pnpm build:framework-core`                      | Build `dist/` and `dist-server/`                                                |
| `pnpm dev:framework`                             | Rebuild both trees on change (`dev:client` and `dev:server` in watch mode)      |
| `pnpm --filter framework-core run build:types`   | Emit `.d.ts` declarations next to the sources (git-ignored)                     |
| `pnpm --filter framework-core run check:surface` | Check the custom-component import surface against the package's runtime modules |

`pnpm build:widget`, `pnpm build:app`, and `pnpm build:release` run `build:framework-core` first. `pnpm dev` runs `dev:framework` alongside the login app. The release chain runs `build:types` through the widget's `build:types` script, and `scripts/copyTypes.mjs` copies the declarations into the published `dist/core/`.

## How Consumers Resolve Core

Consumers keep importing through the path aliases below. The `loginFrameworkDist` Vite plugin (`vite-plugin-dist.ts`) maps each alias onto the built output: `dist/` for client resolutions and `dist-server/` for SSR resolutions. If the package has not been built, resolution fails with a hint to run `pnpm build:framework-core`.

| Alias         | Source path        | Description                                          |
| ------------- | ------------------ | ---------------------------------------------------- |
| `$core`       | `core/`            | Root-level core modules (stores, config, interfaces) |
| `$components` | `core/components/` | Svelte UI components                                 |
| `$journey`    | `core/journey/`    | Journey and authentication flow logic                |
| `$locales`    | `core/locales/`    | Internationalization strings                         |

Each alias also accepts sub-paths (`$core/*`, `$components/*`, and so on). The aliases are declared in `core/tsconfig.json` for type checking.

Unit tests (Vitest), Storybook, and the TypeScript config still resolve the aliases to source, so core tests and stories run without a build.

The IIFE widget bundle inlines the built core. The ES widget bundle inlines it too, per the widget's Vite config.

## Custom Component Surface

Custom components import from the curated `$login-framework` module (`experimental/custom/login-framework.ts`) and must not reach into core directly. `login-framework-surface.ts` checks that every re-export in that file is explicitly named, points inside the package's runtime modules, and uses only the reviewed external type imports. Run `check:surface` after changing the surface file.

## Key Modules

```
core/
├── _effects/            # Cross-cutting side effects (theme, etc.)
├── _utilities/          # Shared utility functions (i18n, errors, theme)
├── components/          # Svelte UI components shared across consumers
├── journey/             # Journey/authentication flow logic
│   ├── _utilities/      # Data analysis, metadata, step utilities
│   ├── callbacks/       # One directory per AM callback type
│   ├── stages/          # Step groupings (login, otp, qr-code, ...)
│   ├── config.store.ts  # Journey configuration store
│   └── ...
├── locales/             # i18n locale strings
├── oauth/               # OAuth store and logic
├── oidc/                # OIDC client store
├── protect/             # Ping Protect store
├── server/              # SvelteKit-only utilities (not built into dist)
├── user/                # User info and token stores
├── collect-entries.ts   # Runtime module list shared by both builds
├── component.store.ts   # Widget component lifecycle store
├── constants.ts         # SvelteKit constants (not built into dist)
├── interfaces.ts        # Shared TypeScript interfaces
├── links.store.ts       # Links configuration store
├── locale.store.ts      # Locale/content configuration store
├── package.json         # Workspace package manifest
├── style.store.ts       # Styling configuration store
├── tsconfig.json        # TypeScript config with path aliases
├── vite-plugin-dist.ts  # Consumer-side resolver for dist and dist-server
├── vite.config.ts       # Client build
└── vite.config.server.ts # SSR build
```

## Type Declarations

`build:types` runs `tsc -p tsconfig.declarations.json` and writes `.d.ts` files next to a fixed list of store and interface sources. These files are generated and git-ignored. They are only needed for the published widget types.
